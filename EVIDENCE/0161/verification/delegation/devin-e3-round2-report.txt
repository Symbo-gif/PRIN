## Findings

### R2-01 — Medium — junction/link coverage inside the retained generated root is still incomplete
`validate_run_record_rev3.py:820-829` (F1, S1 on `generated`), `:830-833`, `:859-863`

`linked_ancestors` is applied to `generated` itself and its ancestors, but `pub` (`generated/publication`) and `inputs` (`generated/inputs`) are descendants — not ancestors — so a junction **at** `generated/publication` or `generated/inputs` is invisible to S1, while F1's `p.is_dir() and not p.is_symlink()` is `True` for a junction (`Path.is_symlink()` is `False` for junctions — the same blind spot F-01 documented in the driver). Inside the trees, `pub.rglob("*")` / `inputs.rglob("*")` keep only `p.is_file()`, which follows links: a symlinked *file* inside `publication/` is inventoried and hashed through the link, and a junction *directory* inside it is recursed into as a normal directory.

*Scenario:* `generated/publication` is replaced by a junction to a staging tree holding byte-identical files. F1 passes (junction is a dir, not a symlink); S1 passes (`publication` is not an ancestor of `generated`); F2/F3 pass (each file still matches its own recorded digest). Every F-check green, yet the retained root is not the real directory F1's name claims. The recorded-digest binding limits this to a structural — not content — forgery, but S1 was specifically introduced to close link substitution and does not cover the roots' own level or contents.

*Fix:* in the F block, reject `is_symlink()` **or** `is_junction()` on `generated`, `pub`, `inputs` (or run `linked_ancestors` on `pub` and `inputs`), and while inventorying `rglob` entries reject `entry.is_symlink() or entry.is_junction()` rather than relying on `p.is_file()`.

### R2-02 — Medium — rev3's narrower G1 silently accepts dirty/untracked files rev2 rejected
`validate_run_record_rev3.py:785-809`, replacing rev2 `:587-612`

Rev2's G1 parsed `git status` and failed on *any* difference except untracked `benchmarks/results/EXP-002/` and the log; G2 required no tracked file to differ from HEAD. Rev3 replaces both with `git diff --name-only SOURCE_SHA -- <frozen_paths>` where `frozen_paths` = `python`, `crates`, the driver file, `benchmarks/_common`, `tests`, `tools`, `paper`, `parity`, `preregistration.md`, `e2-review.md`. Consequently a modified tracked file outside that list — `.github/`, `pyproject.toml`, other `benchmarks/campaign/` modules, `benchmarks/results/EXP-001/*`, or the validator itself under `EVIDENCE/` — and any untracked non-`*.py`/`*.pth` file anywhere in the checkout now pass validation unremarked. `LOG_REL` (`:46-48`) is now dead code.

*Scenario:* re-validating at a descendant commit while `benchmarks/campaign/exp001_driver.py` and an untracked `notes.txt` are modified: rev2 reported them as stray; rev3 reports a clean G1. This does not affect record admissibility (the frozen set covers everything that can influence a record — driver, inputs, protocol — and the relaxation to descendant HEADs is adjudicated), but the coverage drop is a quiet semantic change beyond what the adjudication states ("accepts any HEAD that descends from R"), and a modified copy of the validator itself is now invisible to it.

*Fix:* disclose the reduced scope explicitly, or add a second, non-fatal drift report for non-frozen paths; delete the unused `LOG_REL`.

### R2-03 — Low — retention checks are silently absent on relocated validation
`validate_run_record_rev3.py:812-813`

`publication and (not args.allow_outside_raw_root or args.generated_root is not None)` — a publication-mode copy validated with `--allow-outside-raw-root` and no `--generated-root` emits **no** F1–F4 lines at all; the summary simply reports fewer checks as all-pass. Nothing in the output indicates retention was never checked. Similarly, without `--exact-out-dir`, S6's exact-`out_dir` check is dropped and only the rev2 tail rule (`parts[-4:]`, `:484-488`) applies — a wrong-but-plausible `out_dir` still passes.

*Fix:* emit an explicit `F0 retention checks not applicable/skipped` result line so an absent check cannot masquerade as a pass.

### R2-04 — Low — `font_cache.sha256: null` is a genuine driver output that rev3 rejects
`validate_run_record_rev3.py:736-748` vs `exp002_driver.py:972-979`

`_font_cache_state` returns `{"name": cache.name, "sha256": None}` when the fontlist JSON does not exist — a legitimate driver emission. Rev3's E3 requires `fc["sha256"]` to be a 64-hex string, so a genuine record rendered on a machine without a font cache file would fail. Inherited from rev2 (the check is unchanged in intent), but it remains a hard-coded-schema-versus-emitter mismatch worth recording for E4/E5.

*Fix:* either keep and document the "a font cache must exist" policy, or accept `sha256: null` (still requiring the `name`/`sha256` key set) — noting it weakens the "fonts were hashed" half of the same check anyway.

### R2-05 — Low — S5 elapsed-vs-wall tolerance can false-fail a genuine record on clock adjustment
`validate_run_record_rev3.py:585-606`

`elapsed_seconds` is a `time.monotonic()` delta; `started/recorded_at_utc` are wall-clock `datetime.now(UTC)`. `abs(wall - elapsed) <= 1.0` is correct for the recorded runs (largest observed difference 0.0013 ms), but a >1 s system-clock step (NTP slew) between `started_at` and `recorded_at` would make a genuine record fail. Rare; a wider tolerance or a documented assumption would make the failure mode explicit rather than surprising.

### R2-06 — Low — mutation-test evidence gaps and loose expectations
`mutation_test_rev3.py:146-152`, `:439-446`, `:139-143`, `:574-579`

- `flipped_byte_without_manifest_update` names B2 but fired **S3** in all five transcripts — the mid-file XOR broke JSON before the digest recompute ran. The "content tampered, manifest unchanged → B2" path is therefore not directly demonstrated (B2 is exercised only manifest-side: `manifest_stale_digest`, `manifest_bytes_float`, `manifest_missing_entry`). A flip inside a string value (keeping JSON valid) would exercise it.
- `case_family_changed` expects `["E2","S4"]`, but changing `family` to `C09` cannot trip S4 — the key set is unchanged; only E2 fired. The `S4` expectation is dead weight.
- `label_renamed` expects `["A1"]` and also trips C1 `run_id` (shown in transcripts) — the `any()` rule tolerates the collateral, which is acceptable but means "the check it names" is only weakly bound.
- Still unexercised: run directory itself a link (only an ancestor is tested), `approval_date_utc`, out-of-order/naive timestamps, `elapsed_seconds: true`, a non-C02 case carrying `K`/`alpha_radians`, a C02 case missing them, file-record `raw_bytes: true`/non-hex digest, duplicate keys inside `manifest.json`, and a record-side `files[]` shrink (F2 `record-only`). The D5-HEAD and G1 checks are inherently unmutable (bound to the real repository) — worth stating as a limitation rather than a gap.

### R2-07 — Low — `merge-base` calls have no timeout/capture and pass `commit` unvalidated
`validate_run_record_rev3.py:497-505`, `:527-529`

Both `subprocess.run(["git","merge-base","--is-ancestor",...])` calls omit `timeout` (the `git()` helper uses 60 s) and `capture_output`, and `str(commit)` reaches git argv before any hex validation — a non-hex value is interpreted as a git *option* (e.g. `--all`), not injected (list argv, no shell), and the outcome still fails closed. Cosmetic robustness, inconsistent with the helper.

### R2-08 — Low — `cmd /c mklink /J` and junction-unaware `rmtree` in the harness
`mutation_test_rev3.py:392-405`, `:96-99`

- `cmd /c` receives `mklink /J <path> <target>` via list argv; `list2cmdline` quotes only whitespace-containing args, so a scratch path containing `&`, `^` or `%` but no spaces would be interpolated into the cmd line unquoted — a command-chaining surface. Operator-supplied path, local self-test only, but a `win32`-native junction call or explicit quoting removes it.
- `fresh()`'s `shutil.rmtree(root)` cleanup runs after `junction_ancestor` leaves `root/benchmarks` as a junction. Junctions are not symlinks; `rmtree` recurses through them and deletes the *target's* contents. Contained here (`real_benchmarks` sits inside `root`), but fragile — a junction pointing outside the scratch root would produce out-of-scope deletion on the next case's cleanup.
