## Findings

**R2-F1 — Low — `_git_environment()` matches `GIT_` case-sensitively on a case-insensitive platform**
`exp002_e4_analysis.py:810-812` strips keys with `key.startswith("GIT_")`. Windows environment variable names are case-insensitive: an ambient `git_dir` / `Git_Work_Tree` set by a harness or IDE would survive the strip and be inherited by the child git process (Win32/MSYS2 env resolution is case-insensitive). Consequence is bounded — every git object the module consumes is pinned to a validated 40-hex SHA or a pinned SHA-256 blob digest, so a redirected repository produces `AnalysisError`, not a false verification — but the fix is free:
`return {key: value for key, value in os.environ.items() if not key.upper().startswith("GIT_")}`.
The new test only exercises uppercase `GIT_DIR`/`GIT_WORK_TREE`, so it would not catch this.

**R2-F2 — Low — F5's OSError wrapping is incomplete for global-context listing paths**
`_load_verified_files` now wraps `run_dir.iterdir()` (`exp002_e4_analysis.py:1855-1858`) and `_read_regular` wraps `stream.read()` (713-716), but three global read paths still leak a bare `OSError` out of `verify_context` instead of `AnalysisError`:
- `results_dir.glob("*.json")` at line 1048 — a transient I/O fault (antivirus lock, ACL error) scanning the frozen reference results directory;
- `raw_root.iterdir()` at line 1099 — same for the raw record root inventory;
- `Path(__file__).read_bytes()` at line 972 in `_module_identity`.

Concrete scenario: a permission error on `benchmarks/results/EXP-002` listing → raw `OSError` traceback instead of the `ANALYSIS NOT COMPLETED` diagnostic from `main` (which only catches `AnalysisError`). Still fail-closed — `analyse()` (and therefore any write) runs only after `verify_context` returns — so this is diagnostic hygiene, not a decision-path defect. Suggested fix: wrap these the same way the record-level listing is now wrapped.

**R2-F3 — Low — F3 re-derivation bakes in a sorted-serialization assumption that is only verified transitively**
`check_api` requires `missing == sorted(context.frozen_contract - set(observed))` and `extra == sorted(set(observed) - context.frozen_contract)` (1236-1241). `verify_api_surface` itself returns unordered `set`s (`_deprecation.py:102-103`), so the ordering comes from the driver's serialization of the two sets — outside the file set I was permitted to read this round. The module comment asserts the driver stored both sorted, and the sibling record fields (`expected_names`, `legacy_names`, `input_records`) are all verified against sorted order, so a non-sorting driver would already be inconsistent. But if `collect_api` emitted set-iteration order for these two fields, every genuine api record becomes inadmissible → H1 INCONCLUSIVE. Deterministic and fail-closed (a wrong verdict is impossible), but worth pinning: a one-line test that the driver's emitted `frozen_missing`/`frozen_extra` equal `sorted(set(...))` on a synthetic `module_all` would close the gap independent of the comment.

**R2-F4 — Low (tests) — F1's expanded equality has no distinguishing test**
`_run` now compares all registration fields except `runs` via `dataclasses.replace(..., runs=())` (`test_exp002_e4_analysis.py:496-509`) — correct and complete as stated. However, every current test that diverges from the seed context does so via `source_sha` (re-committing) or `input_manifest_sha256` (mutating `builder.docs`) — both of which the *old* condition already caught. No test exercises a fast-path-triggering change confined to the newly compared fields (`protocol_commit`, `protocol_sha256`, `approval_date_utc`, `reference_api_sha256`, `public_api_sha256`, `deprecation_sha256`).

Concrete scenario it guards: a test that edits `builder.repo`'s working `REFERENCE_API_PATH` file without committing — `reference_api_sha256` is computed from the working file at `write()` time, so the digest changes while `source_sha`/manifest stay equal. Old code → stale `legacy_names` reused silently; new code → falls back to full `verify_context`, which re-derives from the changed file. Related inherent caveat (unchanged by F1): the fast path skips all working-tree checks (`PROTOCOL_PATH` bytes, frozen-input bytes, raw-root inventory) on `builder.repo`; tests that dirty the working tree must call `run_analysis` directly — as `test_changed_working_protocol_aborts` already does. Suggested fix: one test asserting that a working-tree-only mutation of `REFERENCE_API_PATH` through `_run` does not reuse the seed context (e.g., changes `legacy_names` or aborts).
