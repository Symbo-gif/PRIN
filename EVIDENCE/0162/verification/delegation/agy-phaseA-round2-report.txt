## 2. In-Depth Analysis of F3 Re-Derivation (Ordering, Duplicates, Sets)

Per Section 2 of the Round 2 brief:

### Could F3 reject a genuine driver record?
**No.**
1. **Ordering of `observed_names`:**  
   The driver records `"observed_names": list(prin.__all__)`. In `check_api`, analysis casts this to a set via `set(observed)`. Set difference operations `context.frozen_contract - set(observed)` and `set(observed) - context.frozen_contract` are completely order-independent.
2. **Duplicates in `observed_names`:**  
   In the driver, `verify_api_surface(prin.__all__)` converts `module_all` to `current = set(module_all)` before computing `FROZEN_PUBLIC_API - current` and `current - FROZEN_PUBLIC_API`. In `check_api`, analysis computes `context.frozen_contract - set(observed)` and `set(observed) - context.frozen_contract`. Because both driver and analysis deduplicate via `set()`, identical set differences are produced. The record passes admissibility checks in `check_api`. In `adjudicate_h1`, duplicate names are caught by `duplicates = sorted(name for name, count in counts.items() if count > 1)`, contributing to `counterexamples` and resulting in `REFUTED`, strictly satisfying Pre-registration Section 4.1.
3. **The `sorted()` of a set:**  
   The driver performs `sorted(missing)` and `sorted(extra)`. In `check_api`, analysis checks against `sorted(context.frozen_contract - set(observed))` and `sorted(set(observed) - context.frozen_contract)`. Both driver and analysis execute Python 3's built-in `sorted()` over `set[str]`, which relies on deterministic lexicographical Unicode code-point ordering. The resulting lists are identical in content and order.

### Could F3 accept an inconsistent record?
**No.**
- If a corrupted or tampered record carries forged `frozen_missing` or `frozen_extra` (e.g. asserting `[]` despite missing exports, unsorted lists, or duplicate items), `missing == sorted(...)` or `extra == sorted(...)` evaluates to `False`, immediately raising `RecordError` and marking the record inadmissible.
- If `observed_names` deviates from the 175 expected symbols, `adjudicate_h1` catches the discrepancy via `unexpected_exports`, `removed_exports`, or `frozen_contract_{missing,extra}` and issues a `REFUTED` verdict.

## 3. Findings

### [R2-F1] Low: Tests' fast path invalidation (F1) is unexercised by any negative test
- **Location:** [`tests/test_exp002_e4_analysis.py:500-502`](file:///C:/dev/PRIN/tests/test_exp002_e4_analysis.py#L500-L502)
- **Concrete Scenario:**  
  The fast-path check in `_run(builder)` was improved in round 2 to invalidate whenever any global registration field differs:
  ```python
  if context is not None and dataclasses.replace(
      registration, runs=()
  ) == dataclasses.replace(context.registration, runs=()):
  ```
  However, all existing tests verifying that global registration mismatches abort call `_assert_aborts(builder, registration, ...)`, which directly invokes `analysis.run_analysis(...)`, completely bypassing `_run(builder)`. No test in the suite mutates a global registration field (such as `deprecation_sha256`, `public_api_sha256`, or `reference_api_sha256`) and then runs `_run(builder)`. If line 500 were reverted to the round-1 condition (`registration.source_sha == ... and registration.input_manifest_sha256 == ...`), all tests in the test suite would still pass.
- **Suggested Fix:**  
  Add an explicit test asserting that `_run(builder)` bypasses `builder.base_context` when a global registration field changes:
  ```python
  def test_run_fast_path_invalidates_on_global_registration_change(
      builder: Builder,
  ) -> None:
      registration = builder.write()
      bad = dataclasses.replace(registration, deprecation_sha256="0" * 64)
      # Invoking _run or monkeypatching builder.write to return `bad` must
      # trigger full run_analysis and abort, rather than reusing base_context.
      with pytest.raises(analysis.AnalysisError, match="section 1.1 digests"):
          analysis.run_analysis(builder.repo, bad)
  ```
