## Findings

**F1 — Medium — fast-path context reuse can mask mutated global inputs (test harness)**
`tests/test_exp002_e4_analysis.py:479-490`. `_run()` reuses the session-verified `base_context` when only `source_sha` and `input_manifest_sha256` match. `verify_context` also binds `protocol_commit`, `protocol_sha256`, `approval_date_utc`, and `reference_api_sha256` — none are compared.
Scenario: a record-level test mutates `builder.repo`'s `REFERENCE_API_PATH` `__all__` to a different 172-name list (or edits the protocol file / approval date) and calls `_verdicts(builder)`. `builder.write()` recomputes the pin, so `source_sha`/`input_manifest_sha256` still match → fast path → `check_api` validates the record against `context.legacy_names` from the *old* file. The mutation is invisible: H1 stays CONFIRMED instead of aborting/refuting, so the test passes for the wrong reason and silently validates against stale frozen data. `run_analysis` would re-read the file, re-pin, and re-derive.
Fix: guard on all six global fields — e.g. `registration == dataclasses.replace(context.registration, runs=registration.runs)` or an explicit six-field compare — leaving `runs` free to differ.

**F2 — Low — frozen-results inventory counts only `*.json`**
`exp002_e4_analysis.py:963-970`. `present = sorted(path.name for path in results_dir.glob("*.json"))` is compared to the manifest, so a stray non-JSON entry in the reference results directory evades the stated "holds exactly the 172 manifested JSON inputs" invariant. No verdict can change (non-JSON files cannot be inputs), but the global check is weaker than its contract. Fix: `iterdir()` the full inventory or additionally assert no non-`.json` entries.

**F3 — Low — `frozen_missing`/`frozen_extra` are trusted record fields though re-derivable at R**
`exp002_e4_analysis.py:1134-1140`, counted at `:1935-1936`. Every other re-derivable field is re-derived (expected/legacy names, `legacy`, `ownership_present`, row class, all 62 H2 records). The frozen contract `RC1_PUBLIC_API` is a literal tuple in `python/prin/_public_api.py`, pinned transitively by `source_sha`; the module could read the blob at R (same mechanism as the Migration Guide) and require `frozen_missing == sorted(RC1 - observed)` / `frozen_extra == sorted(observed - RC1)`. As written, a record whose frozen sets are inconsistent with its own `observed_names` and the pinned tuple passes — the only unverified driver-computed identity in the record — and the RC1 contract is a different set than the 172+3 population, so it is not redundant with `removed`/`unexpected`. Practical impact needs a driver-side miscount in a trivial set-diff, hence Low. Fix: ast-literal-eval the tuple at R; mismatch → `RecordError`.

**F4 — Low — `OWNER_MATRIX` row 4 abridges the §5.3 owner cell**
`exp002_e4_analysis.py:364-367`. The registered row's owner reads "EXP-004 backend qualification and EXP-005 scientific replication; their CUDA-derived directions are not substituted with CPU measurements here"; the module drops the second clause, so `coverage-and-deferrals.md` renders a truncated cell under a heading claiming the §5.3 matrix (§8.1 requires the matrix). Fix: copy the owner cell verbatim.

**F5 — Low — raw exceptions escape instead of `AnalysisError`/`RecordError`**
`exp002_e4_analysis.py:850-865` (`ast.parse`/`ast.literal_eval` can raise `SyntaxError`/`ValueError`), `:868-885` (`.decode("utf-8")` → `UnicodeDecodeError`), and `:1755,1807-1838` (`run_dir.iterdir()` or mid-stream `OSError` propagates past `load_record`'s `except RecordError`). A present-but-unreadable run directory crashes the whole analysis rather than marking that record inadmissible — contrary to "record-level problems are reported, never fatal". Unreachable for the pinned real records; robustness/consistency gap. Fix: wrap these into `AnalysisError`/`RecordError`.

**F6 — Low — calendar dates are shape-checked but not validated**
`exp002_e4_analysis.py:796-812` and `:614-622`. The driver's `_approval_date` strptime-validates the approval date and `_utc_stamp` validates the run-name stamp; the module accepts any `\d{4}-\d{2}-\d{2}` / `\d{8}T\d{6}Z` shape. Registration is trusted code, so `REGISTERED` is unaffected; fabricated registrations used by tests could carry nonsense dates. Fix: mirror the driver's `datetime.strptime` checks.

**F7 — Low — `_git` inherits ambient `GIT_*` environment**
`exp002_e4_analysis.py:769-787`. With `cwd=repository_root` but inherited env, `GIT_DIR`/`GIT_WORK_TREE`/`GIT_OBJECT_DIRECTORY` redirect every query. Scenario: `GIT_DIR` pointing at a stale clone containing the same history makes ancestry/blob checks (protocol at F/R, guide+baseline at R) run on a different object database while file checks run on `repository_root` — mixed-source verification that mostly fails closed but verifies the wrong provenance. Fix: scrub `GIT_*` variables from the subprocess env (the test harness already does the equivalent).

**F8 — Low (cosmetic) — dead constants**
`exp002_e4_analysis.py:277-292`. `_CASE_KEYS` and `_C02_EXTRA_KEYS` are never referenced; `_exact_keys(case, set(expected))` already covers both cases. Harmless; use them or drop them.
