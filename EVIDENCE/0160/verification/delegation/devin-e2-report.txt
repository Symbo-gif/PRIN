# Cold self-audit — EXP-002 E2 approval round (read-only)

Scope reviewed: `delta-code.diff` / `delta-records.diff` since `0d4278d`, plus the live files `benchmarks/campaign/exp002_driver.py`, `tests/_basetemp.py`, `tests/conftest.py`, `tests/test_basetemp.py`, `tests/test_0160_manifest.py`, `crates/prin-kernels/src/compat.rs`, `.github/workflows/python.yml`, `ci/lint-constraints.txt`, `preregistration.md`, `e2-review.md`, the four `EVIDENCE/0160/verification/e2-review/` scripts/logs, and the pre-remediation driver snapshot `EVIDENCE/0159/verification/full-gate/0159-publication-validation-proposal.py.txt` (which reproduces the `6314532`-era `_pdf_parts`/`_normalized_pdf` verbatim).

## Findings

### F1 — MEDIUM: relative `--basetemp` is resolved against cwd, not pytest's `rootpath`

`tests/_basetemp.py:80` (`target = basetemp.resolve()`), called from `tests/conftest.py:237` with `Path(given)` unjoined to rootpath. pytest resolves a *relative* `--basetemp` as `config.rootpath / basetemp` in `TempPathFactory.getbasetemp()`; the hook resolves it against the process cwd.

**Scenario:** `cd tests && pytest --basetemp=.pytest_basetemp` — pyproject makes rootpath `C:\dev\PRIN`, so pytest deletes `C:\dev\PRIN\.pytest_basetemp`; the hook instead deletes `C:\dev\PRIN\tests\.pytest_basetemp`, a directory pytest would never touch — while the real stale basetemp stays stale. The guard at `_basetemp.py:82` refuses only rootdir/ancestors, so a same-named directory inside the tree that held unrelated content is removed (data loss pytest's lazy deletion would not have caused), and the WinError-32 failure mode the hook exists to fix is not fixed on the path pytest actually uses. All documented invocations run from the repo root (cwd == rootpath), so the standard gate is unaffected; the divergence is confined to invocations with cwd ≠ rootpath.

### F2 — MEDIUM-LOW: `remove()` errors other than `PermissionError` crash the session at startup

`tests/_basetemp.py:85-92` catches only `PermissionError` inside the `while target.exists()` loop.

- **Scenario A (same transient class the hook targets):** an AV scanner, indexer, or second pytest process removes/quarantines the stale tree between `target.exists()` and `shutil.rmtree` → `FileNotFoundError` (or `NotADirectoryError` if it is replaced by a file) propagates out of `pytest_sessionstart` → internal error → the *entire* suite aborts at session start, worse than the single `tmp_path` setup error the hook prevents.
- **Scenario B (pytest-xdist):** every worker runs `pytest_sessionstart`; with `-n N --basetemp=X` all N workers race on the same tree. Losers' `rmtree` hits `FileNotFoundError`/`NotADirectoryError` and the worker dies at startup. (`parity.yml` runs `-n auto` but passes no `--basetemp` today, so this is latent.)
- **Scenario C:** `--basetemp` naming an existing plain file → `NotADirectoryError`, uncaught (pytest itself would also fail here, but via a different path).
- Related minor semantics: the hook deletes eagerly even when no collected test will request `tmp_path` (e.g. `pytest --collect-only`, `-k`/`-m` filters) — pytest's own deletion is lazy, so the hook can delete a directory a given pytest run would never have removed; and `while target.exists()` has no bound on *successful* iterations, so a process that re-creates the directory faster than it can be deleted spins with no sleeps (improbable).

### F3 — LOW-MEDIUM: `sensitivity_bytes` size is never recorded, but amended §8.1 requires "sensitivity sizes/digests"

`exp002_driver.py:1053-1060` records only `sensitivity_sha256`; `_FILE_INT_KEYS` (`:178`) has no `sensitivity_bytes`. But `preregistration.md` §8.1's amended `reproduction-comparisons.csv` row requires "reference/PRIN/repeat raw, normalized and sensitivity sizes/digests". For `.tex` the sensitivity size equals `raw_bytes` and for `.png` it equals `normalized_bytes`, but for `.pdf` the masked-in-place length differs from both (each `/(K) ...\(...\)` becomes `/\1 (normalized)`, length change = `len("(normalized)") − len(original value)`), so it is **not derivable** from the manifested record.

**Scenario:** at E4 the analysis either drops the sensitivity-size column (a protocol deviation against §8.1) or recomputes `sensitivity_bytes` from the retained `publication/` roots — artefacts outside git whose integrity is only verified at E5 (decision 8). Either path weakens the registered artefact contract or couples the sensitivity verdict to unverified bytes. Adding one integer field per file would close it.

### F4 — LOW: `sensitivity_bytes` selects the Info object by `(number, generation)`; the `6314532` policy masked by object *number*

`exp002_driver.py:957-963` masks only `key == info_key`. The pre-exposure code (`0159-publication-validation-proposal.py.txt:119-131`) applied the identical regex to **every** in-use object whose `number == info_number` — including a different-generation object of the same number (the F-B false-equality path fixed in remediation).

**Scenario:** a PDF with `/Info 9 0 R` plus an in-use `9 1 obj` gets `9 1` masked under the `6314532` policy but not under `sensitivity_bytes` → the recorded sensitivity digest differs from what the pre-exposure policy would have produced. Unreachable from the registered writers (Matplotlib's single-revision output uses generation 0 for every object), so no realistic E3 consequence; but the registered claim is digest-faithfulness to `6314532`, and on admissible-but-crafted containers it is not exact.

**Companion (same finding, benign direction):** `sensitivity_bytes` reuses the *hardened* `_pdf_parts` (bounded digits, repeated-trailer-key rejection, unparseable-`/Info` rejection) rather than the weaker `6314532` parser, and `_validate_png` rather than the weaker `6314532` one. So the sensitivity digest's *acceptance set* is the post-exposure one. This can never produce a different recorded digest on accepted inputs — and because `normalized_bytes` (which is strictly stricter, adding `_canonical_info`) runs **first** at `:1051`, `sensitivity_bytes` can never raise where the approved policy does not. **No input aborts E3 because of `sensitivity_bytes`.** The deviation is fidelity-of-model on non-Matplotlib containers, not an execution risk.
