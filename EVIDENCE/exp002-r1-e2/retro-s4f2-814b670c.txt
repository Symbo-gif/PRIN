    fix(exp002-d1): scope the reference-arm digest tie to the platform the E3 record declares
    
    EXP002D1-S4-F2 (D2). PR #34's push was the first Linux execution of the publication
    parity gate S1 added in d90eeabb, and it failed 28 of 39 reference-arm cases on both
    the parity job and nightly full-suite: 14 figures x 2 formats. All 11 .tex tables
    passed, and every other test in the file passed.
    
    The test asserted that a fresh in-process render by the frozen prinet==3.0.0 reference
    generator reproduces the normalized_sha256 recorded in the committed E3 reference run
    on ANY platform. That claim is false: Matplotlib typesets and rasterizes through the
    host FreeType build and font set. The E3 record was authored on Windows, and the
    record says so itself - environment.platform, a field exp002_driver requires.
    
    This is not a PRIN or reference defect. Both arms shift together, which is why the
    registered H3 comparison passes 39/39 on Linux and on Windows: it renders both arms in
    one process, so platform effects cancel. The only false claim was cross-platform
    byte-identity against a single-platform record.
    
    The fix scopes the byte-exact figure tie to the platform the frozen record declares,
    read from the artefact rather than hard-coded as an OS name, so the branch cannot be
    relaxed by hand and a future record authored elsewhere carries its own scope. On that
    platform - the maintainer's Windows host, where the authoritative local gate runs - all
    39 files are compared byte-exactly, unchanged. Off it the 11 .tex tables are STILL
    byte-exact (they are text and do reproduce), and each figure must still render, be
    non-empty, and survive driver.normalized_bytes, which validates PNG critical chunks and
    the PDF Info/xref structure, so a truncated or malformed figure still fails. A new
    test, test_digest_tie_is_scoped_by_the_records_own_platform, pins the mechanism: the
    record must declare a platform, must carry a digest for all 39 files, and if this host
    IS the authoring platform the byte-exact branch must be the one taken.
    
    Non-vacuity proven by four negative controls driven by a plugin kept outside the
    repository that patches item.module (parity/ has no __init__.py, so a parity.* import
    is a distinct module object the collected tests never use):

      bogus+corrupt-figure platform differs -> 39 passed            (structural branch)

    Controls 1 and 3 are the discriminating pair: the identical corruption fails on the
    authoring platform and passes off it, so the branch is demonstrably selected by the
    record's declared platform rather than by the host OS. Unmodified run on this host:
    94 passed. ruff check, ruff format --check and mypy --strict clean on the changed file.
