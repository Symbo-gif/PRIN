## 3. Detailed findings

### 3.1 A1 — WP scope conformance

**Declared scope** (PSR-029 §6): "loss EMA/gradient/latency hooks, daemon integration, MOTA/MOTP/IDF1/identity switches, and synthetic MOT sequences."

**Delivered:**

| Declared deliverable | File(s) | Status |
|---|---|---|
| Loss EMA/gradient/latency hooks | `hooks.rs` (528 lines) | ✅ Present — `TrainingHooks` with `loss_ema`, `loss_variance`, `grad_norm_ema`, latency window/p50/p95/throughput |
| Daemon integration | `hooks_daemon_integration.rs` (116 lines) | ✅ Present — end-to-end `TrainingHooks` → `SubconsciousState` → `SubconsciousDaemon::submit_state` → `InferenceBackend` → `get_control()` proof |

| Synthetic MOT sequences | `mot.rs` (`generate_linear_sequence`, `generate_crowded_sequence`) | ✅ Present — `Seed`-driven, deterministic |

**Scope boundaries correctly observed:**

1. `MotAccumulator` does not reproduce `evaluate_tracking(sequence, tracker, ...)` — the tracker-wiring is a Python orchestration concern (`python/prin/eval`), correctly recorded as out-of-scope discovery #1 in the handoff note. `prin-daemon` cannot depend on `prin-train` (same tier in `crates/README.md` layering), so this wiring is architecturally impossible in Rust.
2. `TRANSFER`/`ASCEND`/`MIGRATE` event subtypes and the full per-event `RAW` log are not reproduced — the four target metrics only consume `MATCH`/`SWITCH`/`MISS`/`FP` counts, correctly scoped.
3. No `prin-mot` crate was created — both modules live in `prin-daemon`, which is consistent with the Phase-5 roadmap row naming exactly one crate for this phase.

**No undeclared scope shipped.** The `assignment.rs` module is crate-private infrastructure required by `MotAccumulator`, not a separate deliverable. The `stable-vec` lockfile bump (scope decision #4) is routine security hygiene, not a feature.

### 3.2 A2 — Plan/architecture conformance

**Crate layering:** `crates/README.md` specifies `dynamics → metrics/tensor/kernels → sim/train/daemon → py`. The new `prin-dynamics` dependency of `prin-daemon` is an allowed direction (lower → higher). No same-tier or reverse dependency was introduced. The workspace `Cargo.toml` is unchanged — `prin-dynamics` was already a workspace dependency.

**No Python numerics:** All numerical computation (EMA recurrences, Hungarian solver, IoU distances, MOTA/MOTP/IDF1 formulas) lives in Rust. The only new Python is `tools/wp030_mot_fixture.py`, which generates a golden fixture by calling the real `motmetrics` package — it does not implement any metric formula itself.

**Seed flow preserved:** Synthetic sequence generators take `&mut Seed` from `prin-dynamics`, the workspace's sole RNG authority (Plan §4, "explicit state/seeding"). The one derived distribution needed (Box–Muller normal) is local to `mot.rs` rather than promoted to `prin-dynamics`, correctly classified as test/evaluation scaffolding.

**`#![forbid(unsafe_code)]`:** Unchanged in `lib.rs:85`. Grep for `unsafe` in `crates/prin-daemon/src/` returns only the `forbid` attribute itself.

**Typed errors:** Two new `DaemonError` variants (`InvalidParameter`, `MotShapeMismatch`) follow the existing pattern of named-field, `#[error]`-annotated variants. No `panic!`/`unwrap`/`expect` in library code paths.

### 3.4 A4 — Numerical parity

**MOT parity (AC1):** `tests/parity_mot.rs` replays 10 scenarios through `MotAccumulator` and asserts agreement with real `motmetrics` 1.4.0 output committed in `tests/data/mot_reference_cases.json`. All 10 pass, including:

- `with_identity_switch` (IDF1 global min-cost assignment: idf1 0.5)
- `perfect_tracking` (idf1 1.0)
- `max_switch_time_bounded` (reassignment 3 frames after last occurrence with `max_switch_time=1` correctly counted as MATCH, not SWITCH)
- `all_forbidden_frame` (MOTA goes negative, MOTP is `0/0 = NaN`)
- `iou_based` (IoU distance matrix derived from bounding boxes)

**Independent fixture regeneration:** Re-running `tools/wp030_mot_fixture.py` produces a byte-for-byte identical fixture (`fc /B`: no differences encountered), confirming the fixture is deterministic and the `motmetrics` reference values are reproducible.

**Hungarian solver correctness:** `assignment.rs` reproduces the `motmetrics.lap.add_expensive_edges` / `_exclude_missing_edges` two-step NaN-handling recipe (module docs cite both source functions by name). The solver itself is a from-scratch O(n²m) shortest-augmenting-path Hungarian algorithm, independently verified by a property test (`solve_assignment_is_always_optimal_and_valid`) that checks arbitrary small rectangular matrices against an exhaustive brute-force optimum. The `then_some` → `then` bug the handoff note describes (caught before shipping by the property test) demonstrates the test suite's effectiveness.

**Training hooks vs. PRINet 3.0 `StateCollector`:** Handoff note §"Parity-evidence disposition" maps each reference formula to a specific test. The auditor verified the mapping by reading both the reference descriptions and the test implementations; all recurrences match.
